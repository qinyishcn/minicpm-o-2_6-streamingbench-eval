# MiniCPM：原版 Testbed RTC 结果核验

范围：每条件 1 个视频、5 道题，共 10 次回答。
**这是小样本诊断，不能作为完整 125 题性能结果。**

| 输入 | 原版 profile | 答对/题数 | 准确率 | 实际特征包缺失 | 特征置零比例 |
|---|---|---:|---:|---:|---:|
| native4 | no_emulation | 4/5 | 80.0% | 0.000% | 0.000% |
| native4 | lossy | 4/5 | 80.0% | 9.934% | 9.935% |

特征经原版 aiortc 的 UDP/RTP/SRTP 发送；TCP 用于信令，可靠 DataChannel 用于控制与答案。缺包按原 F32 位置置零。没有修改原网络 profile 的带宽、时延、丢包概率或队列容量。
实际特征缺失包括网络与队列丢包以及重组/截止时限造成的不可用，不能当作配置随机丢包率。每包特征载荷 1080 字节，与此前离线 1432 字节预算不同。
当前适配器仅按问题顺序传输指定的原生单帧/四帧特征；视频帧索引保持原生连续。本报告不证明持续原生 FPS 视频编码、传输或推理吞吐率。
GPU 重新编码及受损特征字节哈希重建：True；原始帧缓存核验：True。CPU 审计仅核对保存的哈希与缺包布局，部分丢包的字节级重建需要 --reencode。
metadata_to_result_seconds 从服务器收到元数据计时至完整答案生成，不含端侧编码和答案回传；不是端到端延迟。服务器推理计时包含串行 GPU 队列等待。完整答案一次性返回，未测得逐 token TTFT。
此处原生运行时为 Linux CUDA，与此前 Windows Vulkan 离线实验的数值精度可能不同。各 profile 应与同一 Linux/RTC no_emulation 条件比较。
